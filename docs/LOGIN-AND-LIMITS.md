# 两侧登录方式与平台限制

这份文档记录**微软便笺**和**小米笔记**两侧的登录机制、凭据生命周期，
以及实测确认的**平台限制**。

写它的原因：这些结论都是踩过坑、实测出来的，散在代码注释里。
重新查一遍成本很高，所以集中记在这里。

---

## 一、总览：两侧的登录方式

| | **微软便笺** | **小米笔记** |
|---|---|---|
| **协议** | OAuth 2.0 设备码流程 | 小米账号密码 + 二次验证 |
| **在容器里能做吗** | ✅ 能 | ✅ 能（见下方"三条路"） |
| **需要提前准备** | 注册一个 Azure 应用 | 无 |
| **登录动作** | 打开一个网址输码授权 | 在**本页面**输账号密码 + 验证码 |
| **长效凭据** | `refresh_token` | `passToken` |
| **短效凭据** | `access_token`（约 1 小时） | `serviceToken`（数小时~数天） |
| **续期方式** | 自动（用 `refresh_token` 换） | 自动（用 `passToken` 换证） |
| **续期是纯 HTTP 吗** | ✅ 是 | ✅ 是（约 3 秒） |
| **什么情况下需要重新登录** | `refresh_token` 失效 | `passToken` 失效 |
| **实际有效期** | 长期（月级），会自动续 | 长期（月级），会自动续 |

**共同点**：**两侧都能在无浏览器的容器里长期自动运行**，
都不需要"定期人工重新登录"。

## 二、微软侧：设备码登录

### 一次性准备（约 2 分钟，免费）

去 [Azure 门户 → 应用注册](https://portal.azure.com/#view/Microsoft_AAD_RegisteredApps/ApplicationsListBlade)：

1. **新注册** → 名称随便 → **受支持的账户类型**选含「个人 Microsoft 账户」的那项
2. **重定向 URI 留空**（设备码流程不需要）
3. **身份验证** → **允许公共客户端流** = 「是」
4. **API 权限** → 添加 → **Microsoft Graph** → 委托的权限 → 搜 `Notes` → 勾 **`Notes.ReadWrite`**
5. 复制 **应用程序(客户端) ID**

### 登录

页面上粘贴 client_id → 点「开始设备码登录」→ 页面给一个码 →
打开 [microsoft.com/link](https://www.microsoft.com/link) 输码授权。

**授权一次之后 token 自动续期，不需要再管。**

### ⚠️ 两个容易踩的坑

**坑 1：权限名是 `Notes.ReadWrite`，不是 `ShortNotes.ReadWrite`**

便笺真正的接口是 **Outlook REST**（`outlook.office.com/api/beta/me/notes`），
它认的是 `Notes.ReadWrite`。而 `ShortNotes` 那个端点是给 Windows 便笺 App 用的，
**对个人微软账号根本不存在**（实测返回 400）。

**坑 2：Graph Explorer 里看不到 ShortNotes 权限是正常的**

如果你去 Graph Explorer 想验证权限，注意：
- **必须先登录**，否则权限列表是空的
- **"Modify permissions"标签只列当前地址栏那条查询相关的权限** ——
  地址栏是 `/me` 就永远看不到 Notes 相关的
- 想看全部可用权限，走**头像菜单 → Consent to permissions**

### 另一条通道（`graph.mode = fabric`）—— 不推荐容器用

数据也全，但它的令牌**拿不到 `refresh_token`**，一过期就得人工从浏览器重抓。
**容器里没法用**，只适合本机临时验证。

## 三、小米侧：三条路，容器里只有一条好用

小米登录比微软麻烦，因为**容器里没有浏览器**。
页面上提供了三个入口，但**适用场景完全不同**：

### ✅ 路线 A：账号密码登录（容器里推荐这条）

**位置**：页面「账号与登录 → 小米笔记」卡片**最上方**。

**流程**：输小米账号密码 → 可能弹图形验证码 → 选短信或邮箱收验证码 → 完成。

**全程在本页面完成，不需要浏览器。**

**为什么推荐**：
- 容器里唯一可行的完整登录流程
- 登录后拿到 `passToken`，**之后自动续期，不用再登**

**注意**：小米对**新设备 / 异地登录**会要求二次验证 —— 这是小米的风控，
不是本程序的问题。用密码登录走的是"正常登录"流程，**能通过**。

### ❌ 路线 B：扫码登录（容器里不要用）

**位置**：同一张卡片的下方。

**为什么不推荐**：扫码 / 终端登录产生的都是**新设备**，
小米会要求**交互式安全验证**，而这条链路处理不了 —— **卡住**。

> 在**本机**（有浏览器）可以扫码；在**容器里请用路线 A**。

### ❌ 路线 C：浏览器登录（只有本机能用）

走 Playwright 打开本机 Chrome/Edge 读登录态。
**容器里没有桌面环境，点了必然失败。**

它的价值在于：本机跑过一次后，浏览器 profile 里留下登录态，
之后可以**零请求静默续期**（不碰小米的登录接口，风控风险最低）。

### 兜底：直接粘贴 Cookie

页面微软卡片附近有粘贴框。适用于你已经从别处拿到了完整 cookie。

### 小米凭据的字段构成

| 字段 | 作用 | 特点 |
|---|---|---|
| `passToken` | **换证的原料** | **长效**，存在服务端，最关键的字段 |
| `serviceToken` | 日常调接口 | 短效，过期时用 passToken 换新的 |
| `userId` | 账号标识 | 固定 |
| `deviceId` | 设备标识 | 固定 |
| `cUserId` / `i.mi.com_slh` / `i.mi.com_ph` 等 | i.mi.com 这个 sid 的辅助字段 | 缺了会被判未登录 |

**⚠️ 缺一不可**：`serviceToken` 和 `userId` 任一缺失都会被判"凭据不完整"。
但程序会**自动用 `passToken` 换证补齐**（纯 HTTP，约 3 秒），通常你感觉不到。

## 四、凭据自动续期的实测结论

### 微软侧

`access_token` 约 1 小时过期 → 用 `refresh_token` 自动换新。
这部分是标准 OAuth，稳定。

### 小米侧

**实测：把 `serviceToken` 故意改坏，调接口会 401，然后自动换证成功（约 3 秒）。**

```
续期前：读不了（401，serviceToken 确实过期了）
自动续期：成功（3.0s）
续期后：✅ 能读
```

**所以正常情况下你不需要人工重登。**

**什么时候真的需要重登**：
- 你在小米侧主动"退出所有设备"
- 小米风控要求重新验证
- `passToken` 本身失效

**⚠️ 偶发情况**：续期偶尔会因网络抖动 / 小米限流失败。
程序会**回滚并记日志**，下一轮自动重试，通常自己就好了。
如果日志里出现「**小米凭据正在续期中（本轮先跳过）**」——**那不是故障**，
只是同一时刻有另一条路径在续期，等下一轮即可。

## 五、实测确认的平台限制

### ⚠️ 限制 1：Outlook REST **不接受客户端指定便笺时间**

**这条最重要，直接影响"补建记录的时间"。**

| 尝试 | 结果 |
|---|---|
| `POST /me/notes` 带 `CreatedDateTime` | **被忽略**，返回服务器当前时间 |
| `PATCH /me/notes/{id}` 改 `LastModifiedDateTime` | HTTP 200，但**读回仍是原值** |

**后果**：**从「小米侧 → 便笺侧」补建的记录，云端时间必然是"补建那一刻"**，
而不是内容原本的时间。

**本项目的处理**：
- `link.graph_time_synthetic = 1` 标记这类记录
- **列表排序改用小米侧的时间**（所以你在界面上看到的位置是对的）
- **但微软云端那个时间戳改不了** —— 它仍然是补建时刻

**所以**：**界面显示的位置对，云端字段错**。这两件事得分开看。

### 限制 2：小米的新建接口也不认客户端时间

- **便笺 → 小米「新建」**（`POST /note/note`）：**不认** `createDate`/`modifyDate`，
  一律覆盖成服务端当前时间
- **便笺 → 小米「更新」**（`POST /note/note/{id}`）：**认 `modifyDate`**，
  且保留 `createDate`

**本项目的处理**：新建后**立刻调一次更新接口回填原时间**
（复用新建响应的完整 entry，省掉一次详情请求）。
开关：`xiaomi.honor_original_time`（默认开）。

关掉的话写入量减半，小米侧时间是同步时刻，
**但排序仍正确** —— 因为新建时按原时间升序写入，服务端时间戳单调递增，
列表倒序显示出来仍等于原顺序。

### 限制 3：会话 cookie 只在「退出浏览器进程」时失效

**"会话 cookie 关闭即失效"是个常见但不准确的印象**：
- 只在**退出整个浏览器进程**时成立
- 而且 Chrome/Edge 的"继续上次打开的会话"**连这个都能绕过**
- **关掉标签页完全不影响 cookie**（cookie 是浏览器级的）

**本项目的处理**：用 **`sessionStorage`** 做"关标签页就要求重登" ——
它的生命周期恰好是**标签页**：刷新保留、关掉即清空。
新标签页打开时还会**主动登出服务端会话**，避免"只在前端拦"的障眼法。

### 限制 4：小米 `/note/full/page` 返回顺序是「最旧在前」

不是最新在前。**任何依赖顺序的截断都必须在截断处显式排序**，
不能假设上游顺序。（本项目已在两个 provider 和 engine 里各排一次。）

## 六、访问密码那一层（跟上面两侧无关）

页面本身的访问密码是**第三层**，和微软/小米账号完全独立：

| 层 | 管什么 |
|---|---|
| **访问密码** | 谁能打开这个页面 |
| **微软登录** | 连谁的便笺 |
| **小米登录** | 连谁的笔记 |

**访问密码的规则**：
- 刷新页面 → 保持登录（同一标签页）
- 关标签页再打开 → 要求重新输入
- **30 分钟无操作** → 要求重新输入
- 点「退出登录」→ 只退**这一层**，不影响已保存的小米/微软凭据
